# 第 3 批（续）· 音乐与配音改造说明

> 落地计划书 3.3「音乐 / 语音生成」。
> 核心不是「加一个模型」，而是**把一个长期错位的功能拆回它本来的样子**。

---

## 一、先说清楚问题：音乐和配音不是一回事

改造前的状态是这样的：

| 界面 | 代码 | 实际行为 |
|---|---|---|
| 「音乐合成」tab | `generateMusic()` → `/ai/generate/music` | 调火山 **TTS**，把输入的文字**念出来** |
| 模型下拉 | `ACE-Step` | 项目里**没有** ACE-Step 的任何实现 |
| 前端按钮 | 「生成语音」 | 文案又变成语音了 |

也就是说：**界面说音乐、模型名说 ACE-Step、按钮说语音、后端跑 TTS，四个说法互不相同**。
而且这条 TTS 链路本身也跑不通（见 `Bug清单.md` FIX-10，实测 HTTP 400）。

所以这次改造做了两件事：

1. **补上真正的音乐生成**：本地 MusicGen-small（CPU）
2. **把 TTS 归位到「配音」**，并修正它的请求体让链路真正可用

---

## 二、两条链路的职责边界

```
用户输入一段「氛围描述」
        │
        ├──► 音乐生成 /ai/generate/music ──► MusicGen-small（本地 CPU）
        │         "温柔的钢琴独奏，带雨声"        ↓
        │                                    music_<ts>.wav   （32kHz 立体声）
        │
        └──► 语音配音 /ai/generate/voice ──► 火山 TTS（云端）
                  "雨还在下。她把伞收起来…"        ↓
                                             voice_<ts>.mp3
```

**判断口诀**：
- 输入是「描述声音长什么样」→ 音乐
- 输入是「要念出来的文字」→ 配音

两个入口在数据库里也分开存：`AIGeneration.type` 分别是 `music` 和 `voice`，
前端历史记录据此显示不同标签、走不同的导出分支。

## 三、后端改动

### 3.1 新增 `back/app/ai/backends/music_local.py`

与 `image_local.py` **完全同构**的设计约束（复用已验证过的模式，降低认知成本）：

| 设计点 | 做法 | 原因 |
|---|---|---|
| 懒加载 | 不生成就不加载 | 进程启动零开销，不影响不用音乐功能的用户 |
| 低精度 | 优先 `bfloat16` | Zen4（8945HX）支持 AVX512-BF16，权重内存减半 |
| 内存守卫 | 可用内存 < `MUSIC_MIN_FREE_RAM_GB` 直接拒绝 | 宁可明确拒绝，也不把机器拖进换页 |
| 用完即卸 | `MUSIC_UNLOAD_AFTER=true` 时 `del` + `gc.collect()` | 不常驻，避免和 SD 抢内存 |
| 推理模式 | `torch.inference_mode()` | 关闭梯度记录，压峰值 |
| 零新依赖 | 手写 16-bit PCM wav | 不引入 `soundfile`（它带 libsndfile 二进制） |

关键实现：

```python
# MusicGen 每秒约 50 个 token（frame rate 50Hz）
max_new_tokens = int(max(1, min(duration, 30)) * 50)

sr = int(getattr(model.config.audio_encoder, 'sampling_rate', 32000))
```

**权重格式守卫**（这是踩过的坑，见第四节）：

```python
# 只有 state_dict.bin（原始权重）时 transformers 无法直接加载，
# 提前拦截，避免用户等半天才看到异常
if not any(os.path.exists(os.path.join(model_dir, f))
           for f in ('model.safetensors', 'pytorch_model.bin')):
    raise RuntimeError('MusicGen 权重格式不兼容 ... 请重新下载')
```

- `generate_music_wav()` 原实现（名字叫音乐，实际跑 TTS）

新增：

```python
_MUSIC_CLOUD_ALIASES = ('volcengine', 'cloud', 'tts')

    # 而不是像以前那样拿 TTS 冒充

def generate_voice(user_id, text, voice_type=None, duration=0) -> (bool, dict)
    # 火山 /api/v1/tts 一次性合成
```

保留 `generate_music_wav()` 作为**兼容转调**（内部转 `generate_voice()`），
避免其它模块 import 时直接崩。

**为什么 `volcengine` 分支要报错而不是降级**：
项目确实没有云端音乐 API。静默拿 TTS 顶替，用户拿到的会是一段「念白」而不是 BGM，
比直接报错更糟。报错信息里直接告诉他该选哪个：

```
当前没有可用的云端音乐生成后端。请选择「本地 MusicGen」，
或改用「配音」功能（云端 TTS）。
```

### 3.3 `views.py`：拆路由 + health 扩容

| 路由 | 语义 |
|---|---|
| `/ai/generate/music` | 音乐，body `{prompt, duration, model}` |
| `/ai/generate/voice` | 配音，body `{text, voice_type}`（兼容 `prompt`） |

`/ai/health` 新增两段状态，前端据此做**出图/出音乐前的预检**：

```json
{
  "local_music": {
    "ok": true, "model_exists": true, "loaded": false,
    "dtype": "bf16", "free_ram_gb": 3.71, "need_ram_gb": 2.5,
    "ram_ok": true, "ready": true, "reasons": []
  },
  "tts": {
    "ok": false, "backend": "volcengine-tts",

```

两者都用 `try/except` 包住，**任何异常降级为 `ok=false`，绝不影响 `/ai/health` 整体可用性**。

```ini

MUSIC_MODEL_DIR=                      # 留空用 back/.models/musicgen-small
MUSIC_DTYPE=bf16
MUSIC_DEFAULT_SECONDS=10
MUSIC_MAX_SECONDS=30
```

> ⚠️ **`VOLCENGINE_APPID` 必须是字符串**。它是一串纯数字，一旦被当整数处理，
> JSON 序列化后会变成 `2.124834565e+09`，服务端直接解析失败（FIX-10 的根因之一）。
> 代码里统一 `str(...)` 兜住。

## 四、模型与权重

| 项 | 值 |
|---|---|
| 模型 | `facebook/musicgen-small` |
| 落盘目录 | `back/.models/musicgen-small/`（已 `.gitignore`） |
| 实际占用 | **3.3GB**（含 `pytorch_model.bin` 2.36GB + `compression_state_dict.bin` 236MB + `state_dict.bin` 841MB） |
| 采样率 | 32000 Hz |
| 许可 | CC-BY-NC 4.0（**仅限非商用**） |

### 下载时踩的坑

用 `snapshot_download(..., allow_patterns=['*.json','*.safetensors','*.bin','*.txt'])`
会同时拉三个大文件，其中：

- `pytorch_model.bin`（2.36GB）—— ✅ transformers 能直接加载
- `state_dict.bin`（841MB）—— ❌ 原始权重，`from_pretrained` 用不了
- `compression_state_dict.bin`（236MB）—— ❌ 同上

也就是说**多下了约 1GB 无用文件**。代码里的「权重格式守卫」就是为了在这种情况下
提前给出可读的报错，而不是抛一个 transformers 内部异常。

> 想省空间可以只保留 `pytorch_model.bin` + 各 `*.json` + `tokenizer*`，
> 删掉两个 `*_state_dict.bin`（`compression_state_dict.bin` 是 EnCodec 的量化压缩器，
> 不删也能跑，只是多占 236MB）。

## 五、实测数据（真实权重，CPU）

测试条件：`bf16` / `duration=5` / `guidance=3.0` / `temperature=1.0` / `seed=1234`，
prompt = `gentle piano solo, slow tempo, soft rain in background, calm night`

| 阶段 | 耗时 | 进程 RSS | 系统可用内存 |
|---|---|---|---|
| 启动（未加载） | — | 0.20 GB | 3.71 GB |
| 加载模型 | **4.1 s** | 1.57 GB | 2.21 GB |
| 生成 5 秒音频 | **16.06 s** | 1.72 GB | 2.75 GB |
| 写 wav | <0.1 s | 1.72 GB | 2.75 GB |
| 卸载后 | — | 1.72 GB | 2.81 GB |

**产出**：`audio_seconds = 4.94`（请求 5 秒，差 0.06 秒是 token 粒度）、
`sample_rate = 32000`、文件 **308.8 KB**。

### 由此调整的两个结论

1. **内存阈值从 3.0GB 下调到 2.5GB**
   实测加载后 RSS 只涨 **1.37GB**（0.20 → 1.57），峰值 1.72GB。
   原来拍脑袋定的 3.0GB 会把「本来能跑」的请求挡在门外——改造过程中就真的被挡了一次
   （当时可用 2.82GB < 3.0GB）。现在 2.5GB 阈值 = 实测峰值 1.72GB + 约 0.8GB 余量。

2. **速度参考：约 3.2 倍实时**
   5 秒音频 16 秒出。按此外推：
   - 10 秒 ≈ 32 秒
   - 30 秒 ≈ 96 秒（上限）

   前端「音乐生成」卡片里直接把这个估算显示出来，避免用户以为卡住了。

> 注意：以上是**单个进程独占**的数据。如果同时开着 SD 出图（3.8GB）或 Ollama，
> 内存会不够，这是 15.8GB 机器的硬边界，不是代码问题。

## 八、已知限制

1. **音乐质量受限于 small 模型**
   `musicgen-small` 是 3 亿参数版本，能出氛围/简单旋律，但结构复杂的曲子会糊。
   要更好效果得上 `musicgen-medium`（约 6GB 权重，CPU 上不可行）。
2. **CPU 速度就是 3.2 倍实时**，30 秒上限是刻意的
3. **`CC-BY-NC 4.0` 仅限非商用**，商用需换权重
4. **配音依赖用户自备火山凭据**
   项目里没有内置 `VOLCENGINE_APPID` / `TTS_TOKEN`（这两个值必须去控制台
   「语音技术 → 语音合成 → 应用管理」取）。未配置时接口返回明确提示，不静默失败。
5. **配音链路尚未做真实合成验证**
   契约、请求体结构、错误处理都验证过了，但因为没有凭据，**没有真实发出过一次
   成功的 TTS 请求**。填入凭据后建议先手动打一次接口确认。
6. **Celery 异步未实测**
   Redis（`aigc-redis`，6380）当前未启动，音乐/配音都走同步回退。逻辑与出图一致。
