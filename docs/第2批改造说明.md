## 三、LangChain 上下文管理（3.3.1）

### 替换了什么

原实现（`SceneEdit.vue:generateHistorySummary()`）是前端自制规则：

- 近邻 ≤10 条 → 取前 5 条原文
- 更远 → 按「首 3 条 + 中间 1 条 + 末 3 条」抽样，硬截断到 200 字

这是**固定规则**，与语义无关，且压缩逻辑散在前端。

### 现在怎么做

`ConversationSummaryBufferMemory`：**近期对话保留原文，超出 token 上限的旧对话由 LLM 压缩成摘要**，滚动向前。

关键工程决策：

| 决策 | 原因 |
| --- | --- |
| 用 `langchain_classic.memory` 导入 | LangChain 1.x 已把 `langchain.memory` 移除，该类迁至 `langchain-classic`（由 `langchain` 元包自动带入） |
| **摘要回写 Redis** | `ConversationSummaryBufferMemory` 自身不持久化摘要。若不回写，Celery 每次在新进程执行任务时摘要都会丢，只剩原始消息。已在 `get_memory()` 中恢复 `moving_summary_buffer` |
| **自实现 CJK token 估算** | `ChatOllama.get_num_tokens_from_messages` 会 import `transformers` 加载 tokenizer；本项目 torch 为 CPU 版且 venv 内 `transformers` 因 huggingface-hub 版本冲突不可用，该路径直接抛 `ImportError`。改为「CJK 字符≈1 token、其余≈4 字符/token」 |
| 自实现 `BaseChatMessageHistory` 子类 | 复用项目已有的 Redis 连接（6380/db0，带降级），不引入 `RedisChatMessageHistory` 的第二套连接管理 |

### 两种工作模式

```
stateful = false（默认）  前端把已写剧情 history 传过来 → 后端压缩 → 生成
stateful = true           传 session_id，多轮记忆落 Redis，跨请求累积
```

两种模式都让**前端不再自己拼 prompt**。前端只需发 `history + user_input`。

## 五、FSM 剧情链校验 + branch_paths CRUD（3.3.3）

### 5.1 补上完全缺失的 API

原系统 `branch_paths` 表**只有模型定义、没有任何接口**，仅被「删除项目」和「删除角色」两处间接引用。新增：

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/project/branches/<project_id>` | 列出项目全部分支 |
| POST | `/project/branches/<project_id>` | 新建（**幂等**：同起止不重复建边） |
| POST | `/project/branches/<project_id>/batch` | 批量覆盖写入（剧情树整树保存） |
| PUT | `/project/branches/detail/<path_id>` | 更新 |
| DELETE | `/project/branches/detail/<path_id>` | 删除 |
| GET | `/project/story_graph/<project_id>` | 剧情拓扑 + FSM 校验 |
| POST | `/project/story_graph/<project_id>/validate` | 只做校验 |

写入侧校验：拒绝自环、拒绝跨项目/不存在的节点、批量写入**先全量校验再落库**（避免写一半失败留脏数据）。

### 5.2 FSM 校验的三个设计要点

这一块花的时间最多，因为**朴素实现会产生大量误报**，逐个修掉了：

**① 顺序边（auto_sequence）——最关键**

`branch_paths` 只记录**玩家选择**，「对话 A 之后接对话 B」这种自然顺序播放**不会**产生记录。若只按 `branch_paths` 建图，纯线性剧情会退化成一堆孤立节点，校验结果全是误报。

因此默认开启 `auto_sequence`：为**没有显式出边**的节点，按「场景顺序 → 场景内 order_num」补一条顺序边，还原真实播放流；已配置分支的节点不补（分支取代顺序流）。

**② 选择节点的死端必须按显式边判**

合成顺序边会让「忘配分支的选择节点」在图上"有出口"，从而掩盖死端。所以 `CHOICE_WITHOUT_BRANCH` 单独按**显式边**判定，否则最常见的漏配会被漏掉。

**③ 真分叉才告警**

最初版本对「有出口但不是选择类型」一律告警，线性剧情里每个对话节点都会中招（噪音爆炸）。改为**仅当显式出边 ≥ 2** 才报 `IMPLICIT_BRANCH`。

### 5.3 校验项清单

| 级别 | 代码 | 含义 |
| --- | --- | --- |
| error | `DANGLING_EDGE` | 分支引用了已不存在的节点 |
| error | `NO_START` | 所有节点都有前驱（整体成环） |
| error | `CYCLE` | 死循环（附完整环路） |
| error | `CHOICE_WITHOUT_BRANCH` | 「选择」节点没配任何分支 |
| error | `EMPTY_GRAPH` | 项目无剧情内容 |
| warn | `ORPHAN` | 从主入口不可达 |
| warn | `MULTI_START` | 存在多个无前驱节点 |
| warn | `NO_ENDING` | 无任何可达结局 |
| warn | `DUPLICATE_EDGE` | 同一起止重复建边 |
| warn | `EMPTY_CHOICE_TEXT` | 分支缺选项文案 |
| warn | `IMPLICIT_BRANCH` | 真分叉但不是「选择」类型 |
| warn | `SINGLE_CHOICE` | 「选择」只有 1 个选项 |

输出含 `summary`（节点数/分支数/结局数/路径条数/覆盖率）。

## 八、本轮发现并修复的问题

### FIX-3 缓存命中时跳过记忆写入，导致多轮上下文「原地踏步」 🔴

- **现象**：`stateful=true` 连续两轮后，`GET /ai/memory/<sid>` 读回 `message_count=0`；但任务返回体里却显示 `4`。
- **根因**：`continue_story()` 命中 Redis 缓存后**提前 return**，直接跳过了 `remember_turn()`。于是：
  1. 记忆从未真正写入 Redis → 多轮上下文不推进；
  2. 返回体里的 `memory` 字段来自**被缓存的那份结果**（含上一轮的消息数），所以看起来"正常"，极具迷惑性。
- **为什么第二次运行才暴露**：第一次运行是真实推理，记忆正常写入；第二次运行命中缓存才踩中。这也解释了为何单轮探测正常、连跑两轮才失败。
- **修复**（两处）：
  1. 命中缓存时，若 `stateful`，**仍执行** `remember_turn()` —— 记忆写入是副作用，不属于可缓存结果；
  2. 写缓存前**剥离 `memory` 字段** —— 该字段与会话强相关，缓存会造成跨会话串味。
- **回归用例**：`缓存命中时记忆仍推进（回归）` —— 重复同一输入触发缓存，断言 `message_count` 必须递增（实测 4 → 6）。

### FIX-4 `submitAndWait` 同步模式返回错误层级 🟡

- 后端同步模式返回 `{status, async:false, data:{...}}`，而 `submitAndWait` 直接返回整个信封，导致调用方拿不到 `backend` 等字段（`AiView.vue` 里 `info?.backend` 永远为空）。
- 修复：同步分支改为返回 `res.data`。

### 顺带修正

- `SceneEdit.vue` 原先硬编码 `model: 'deepseek-ai/DeepSeek-V3.2'`（后端不存在该模型，参数被静默忽略），已改为不传，由后端按 `TEXT_BACKEND` 决定。
