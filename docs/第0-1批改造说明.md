## 六、设计要点

### 6.1 降级设计（这是本次的关键取舍）

所有新能力都是**可选的**，缺失时不影响主流程：

| 缺失项 | 降级行为 |
| --- | --- |
| Redis 未装 | 缓存操作静默跳过，接口直查数据库 |
| Celery 未起 | `ASYNC_ENABLED=false` 时接口同步执行，前端行为不变 |
| Ollama 未起 | 若配了 `DEEPSEEK_API_KEY`，自动降级到云 API（`TEXT_FALLBACK_TO_CLOUD`） |
| Redis 挂了但 `CACHE_ENABLED=true` | 启动时探测失败 → 自动 `redis_client=None`，不抛异常 |

这保证了**任何时刻系统都能跑起来**，不会因为引入了新组件而变得更脆弱。

### 6.2 异步兼容设计

`/ai/generate/*` 现在返回两种形态：

```json
// 异步（ASYNC_ENABLED=true）
{ "status": "success", "async": true, "task_id": "xxx" }

// 同步（ASYNC_ENABLED=false，向后兼容）
{ "status": "success", "async": false, "data": { ... } }
```

前端用 `submitAndWait()` 统一处理：见 `task_id` 就轮询，否则直接用返回值。**因此前端可在两种后端配置下都用**。

### 8.5 本轮发现并修复的两个问题

> 这两处是**第 1 批改造时我遗漏的**，在实测中暴露，现已修复。

**【修复 A】默认模型名硬编码导致本地推理被绕过**

- 现象：异步任务返回 `backend: "deepseek(fallback)"`、`model: "deepseek-r1:1.5b"`，明明配了 Ollama 却走了云 API。
- 根因：`views.py` 中 `model = data.get('model', 'deepseek-r1:1.5b')` —— 这是第 2 代遗留的硬编码默认值。前端不传 `model` 时，该值传给 Ollama，而本地只有 `qwen2.5:7b`，Ollama 返回 `404 model not found`，触发降级。
- 修复：默认模型改为跟随配置 —— `TEXT_BACKEND=ollama` 时取 `OLLAMA_MODEL`，否则取 `DEEPSEEK_MODEL`（新增配置项）。修复后 `backend` 正确变为 `ollama`。

**【修复 B】缓存层建好但未接入业务路径**

- 现象：`extensions.py` 里的 `cache_get/cache_set` 完整可用，但连续两次相同 prompt 仍各自推理、生成两条记录。
- 根因：`generate_and_save_text()` 中未调用缓存函数 —— 缓存层是「孤岛」。
- 修复：在生成前按 `md5(user_id|model|length|prompt)` 查缓存，命中即直接返回（`cached: true`）；未命中则推理后写回，TTL 取 `CACHE_TTL`（默认已从 60s 调到 3600s）。
