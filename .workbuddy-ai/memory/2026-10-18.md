## 补充（同日稍晚）：用户反馈「出图还是不成功」的排查

### 真实原因：内存不够（不是 bug）
用户机器日常可用内存只有 **2~4GB**（Edge/QQ/DeepSeek 客户端/llama-server 长期占 10GB+），
而出图需 4.5GB → 被守卫拒绝。用户选择**保持 4.5GB 阈值**（宁可拒绝也不冒卡死风险）。

### 本轮改进
- 错误信息**直接列出该关哪几个程序**（按实际内存占用排序），如
  「建议先关闭：QQ（1.0GB）、Edge 浏览器（0.9GB）、DeepSeek 客户端（0.5GB）」
- `/ai/health` 的 `local_sd` 新增 `ready` / `ram_ok` / `need_ram_gb`
- 前端选了「本地 SD」后点生成会**先查内存再发起**，不再白等一次失败
  （为此补了 `getAiHealth()` 到 `src/api/ai.ts`）
- 新增体检工具 `docs/_src/check_memory.py`：差多少 / 谁在吃 / 关掉哪些能达标

### **FIX-9（🔴 很重要）**：后端「静默消失」的真凶是 reloader
之前多次出现后端请求返回 `HTTP 000`、日志无任何异常，一度误判为内存不足被杀。真因：
`debug=True` 的 watchdog 把 **`site-packages`** 也纳入监视（本项目 venv 混用 `D:\conda` 的包），
加载 torch 期间包内文件变动触发 `* Detected change in ...torch\_inductor\config.py, reloading`，
重载时 socket 重建失败 → `OSError: [WinError 10038]`，服务线程死亡但主进程还在。

**修复**：`manage.py` 改为 `use_reloader=False`，保留 `FLASK_USE_RELOADER=1` 开关。
这与「日志写在 `back/logs/` 导致每写一行重载一次」是**同一机制的两种表现**。
**以后排查后端起不来，先看有没有 `Detected change ... reloading`，不要急着怪内存。**

## 3.3 音乐/配音拆分（已完成）

### 核心结论：原来是「一个功能四个说法」
界面写「音乐合成」、模型下拉写 `ACE-Step`、按钮写「生成语音」、后端实际跑**火山 TTS**，
而且那条 TTS 链路因为请求体结构错误**从未跑通过**（实测 HTTP 400）。
所以这次不是「加个模型」，而是**把错位的功能拆回它本来的样子**。

### 拆成两条独立链路
| 能力 | 路由 | 后端 | 产物 |
|---|---|---|---|
| 音乐（BGM/环境音） | `/ai/generate/music` | 本地 MusicGen-small（CPU） | `music_<ts>.wav` 32kHz |
| 配音（念台词） | `/ai/generate/voice` | 火山 TTS `/api/v1/tts` | `voice_<ts>.mp3` |

判断口诀：**描述声音长什么样 → 音乐；要念出来的文字 → 配音。**
数据库 `ai_generations.type` 用 `music` / `voice` 区分。

### 新增/改动文件
- 新增 `back/app/ai/backends/music_local.py`（与 image_local 同构：懒加载/bf16/内存守卫/用完即卸/手写 wav 不引入 soundfile）
- `services.py`：删掉旧 `generate_music_wav` 实现 + `_poll_volcengine_task`，
  新增 `generate_music()` / `generate_voice()` / `_resolve_music_backend()` / `_static_rel_url()`
- `views.py`：拆两个视图 + `/ai/health` 新增 `local_music` / `tts` 两段（都 try/except 降级）
- `tasks.py`：`task_generate_music` / `task_generate_voice`，`TASK_MAP` 加 `voice`
- 前端：`VoiceGenerator.vue` 改写为「音乐生成」；**新建 `VoiceSynthesizer.vue`（配音，蓝 `#8fd3ff`）**；
  `AiView.vue` tab 3→4；`api/ai.ts` 加 `generateVoice()` + `GenerateVoiceParams`

### 实测数据（MusicGen-small / bf16 / CPU / 5 秒）
- 加载 **4.1s**，RSS 0.20→1.57GB（**只涨 1.37GB**）
- 生成 5 秒音频 **16.06s**（约 **3.2 倍实时**），RSS 峰值 **1.72GB**
- 产出 4.94s / 32kHz / **单声道** / 308.8KB，RMS 0.099 峰值 0.416（非静音非爆音）
- HTTP 全链路实测 200，`/static/music/4/music_*.wav` 可访问

### 由此下调内存阈值 3.0 → **2.5GB**
原阈值是拍脑袋定的，实测峰值才 1.72GB，3.0GB 会把**本来能跑**的请求挡在门外
（改造中就真被挡了一次，当时可用 2.82GB）。现在 2.5 = 1.72 + 0.8 余量。
**教训：阈值要按实测 RSS 定，不要凭感觉。**

### 两个新踩的坑
- **权重格式**：`snapshot_download` 会同时拉 `pytorch_model.bin`(2.36GB，能用) +
  `state_dict.bin`(841MB，不能用) + `compression_state_dict.bin`(236MB，不能用)，
  白下 1GB。`_load()` 里加了**权重格式守卫**提前拦截，给出可读报错。
- **FIX-11 路径分隔符**：`os.path.join('app/static/music/4','x.wav')` 在 Windows 上得到
  `app/static/music/4\x.wav`，落库后前端拼 URL 不可靠。加 `_static_rel_url()` 统一转 POSIX，
  并修了库里 3 条历史记录（id 16/26/84）。
  **以后任何要拼进 URL 的路径都不要直接用 os.path.join 的结果。**

### 环境坑（复用价值高）
环境里有 `HTTP_PROXY=http://127.0.0.1:63801`，**连 127.0.0.1 也会被代理**，
表现为 `502 upstream connect failed`。跑 E2E / curl 本地服务时必须
`NO_PROXY=127.0.0.1,localhost` 或 `curl --noproxy '*'`。**别误判成后端挂了。**
